Teck.Cloud / implementation and acceptance plan / 14 November 2026

Identity, tenants & service access

Keep Keycloak for authentication and fine-grained authorization. Use Organizations for tenant identity and access enablement, a Keycloakify theme for the user experience, and evaluate KETE for event integration with RabbitMQ and Wolverine.

Status: Baseline implemented and verified. Native identity, tenant isolation, MFA, event recovery, coverage and static-handler checks pass. Both Aspire browser journeys and both full/reduced KIND deployments pass. Administrator MFA is enforced at the BFF; services independently enforce trusted-client, role/resource and active-tenant authorization. Tests used disposable WSL resources; no active user sandbox was changed and nothing was published remotely.

What we are choosing

Direction agreed

Keycloak + Organizations

One organization per tenant within a shared realm as the starting design. Keycloak owns membership and identity access enablement. Separate customer/admin gateway clients and downstream service audiences.

Requested theme

shadcn + Keycloakify

Use emirhannaneli/keycloak-shadcn as the requested starting point, built with Bun through Nx. Package the resulting theme JAR into our Keycloak image. Keycloak serves the UI; a separate theme server is unnecessary in deployment.

Opt-in evaluation only

KETE → RabbitMQ

The evaluation passed but found mandatory administrative-data retention, so KETE is excluded from the normal image. Canonical lookup, event invalidation and reconciliation remain the implemented foundation.

A Customer service is not required simply to repeat Keycloak's enabled flag. Add a Customer module or service when customer business data and workflows require it.

1 · A user request

The chart shows logical responsibilities. The service-side authorization component is a shared adapter inside each service, not a new network service.

Start with explicit server-side Keycloak Authorization Services decisions for protected operations, represented as ASP.NET authorization requirements used by FastEndpoints and gRPC. Evaluate permission-bearing tokens later if they improve latency without weakening revocation semantics. Do not assume token exchange preserves organization claims or permissions: prove both on the pinned Keycloak version.

Protocol boundary: application-to-application synchronous calls use gRPC; asynchronous calls use RabbitMQ/Wolverine. Keycloak's OIDC, OAuth, authorization and Admin APIs remain HTTPS protocol integrations.

Administrator trust boundary: the admin BFF checks fresh MFA on every administrative request. Services independently validate the token, require the configured admin exchanger, platform role, Keycloak resource permission and active target tenant. An exchanged token does not independently prove recent MFA; its authorized-party claim identifies the issuing client, not the network caller. Use workload identity and network policy for the latter boundary.

3 · MFA and optional adaptive authentication

Baseline agreed Use Keycloak's built-in WebAuthn/passkeys, TOTP and recovery codes. Later, subject to validation Add GeoAware signals and selected MFA plugins only after the baseline is proven.

CapabilityDecisionImplementation requirement
Administrator MFABaselineRequire strong authentication for admin access, preferably user-verified WebAuthn. Verify the configured assurance level and freshness; a passkey label alone is insufficient. Customer tokens must not satisfy admin access merely through token exchange.
Customer MFA and recoveryBaseline capabilityOffer passkeys and TOTP with recovery codes. Make enrollment/enforcement explicit per client and operation; decide tenant-specific enforcement before introducing it. Do not claim MFA is mandatory for every customer until that policy is selected.
GeoAwareOptional second phaseBegin with notifications and extra verification for unfamiliar logins. Use a maintained local MaxMind database and controlled test fixtures. Do not automatically disable accounts based only on location changes.
Enforce MFA pluginEvaluate only for an enrollment UX gapCompare built-in required actions with choosing among enrollment methods. Upstream labels this module beta. Install only if it solves a demonstrated gap and passes compatibility and enrollment tests.
Trusted Device pluginOptional customer convenienceA signed browser cookie plus server-side credential can represent remembered MFA. Require expiry and revocation. Never allow it to bypass the admin baseline or fresh authentication required for sensitive operations.
SMS/email OTP and mobile pushDeferredNo SMS/email OTP as the default MFA method. Keep built-in recovery available. Mobile push is upstream work in progress and is outside this foundation's scope.

Baseline strength is enforced independently of risk signals. GeoAware's device signal comes from User-Agent information; it is not cryptographic device identity. An unavailable GeoIP lookup must not silently suppress required authentication. Define and test the entire flow's result: a conditional authenticator returning false can skip its subflow.

Only trusted ingress proxies may supply forwarded client IPs; reject spoofed headers and avoid treating the ingress address as the user's address. Define retention and deletion for login IP/location/device history. Scope notifications and audit payloads to necessary data.

These are providers and flow configuration inside the same Keycloak image, not new application microservices. Extend the shadcn theme for any selected plugin's forms and account controls; its standard MFA pages do not establish support for arbitrary provider templates.

Prove the identity and tenant contract

Pin a supported Keycloak image; configure Organizations, separate gateway clients, service audiences, standard token exchange, resource/scope policies and a restricted management client. Use two test tenants and users with different memberships, plus a user belonging to both.

Done when: real-container tests establish exact organization claims, tenant selection, exchange behavior and suspension semantics. Select a bounded access-revocation delay from measured behavior, not assumptions.

Build the theme and reusable image

Create src/apps/keycloak-theme as an Nx/Bun project based on the requested shadcn starter; preserve its license and record the upstream revision. Build the compatible theme JAR with Keycloakify and use a pinned Java/Maven build stage. Package it in a custom Keycloak image with an affected-build target.

The starter contains a separate realm-branding SPI and optional declarative admin UI. Review that feature independently; use static build-time branding initially unless runtime branding is wanted. Do not enable experimental admin UI merely to obtain the shadcn appearance. The Keycloakify-documented shadcn package is an alternative to compare if maintaining starter source proves unnecessary.

Done when: the actual image serves themed login, errors, recovery and relevant MFA/organization screens. Account-console coverage is checked separately; theme branding by realm must not be mistaken for branding by organization.

Establish built-in MFA and recovery

Configure WebAuthn/passkey and TOTP flows, recovery codes and administrator enforcement in the version-controlled realm. Keep customer and admin assurance requirements distinct. Configure enrollment, reset and recovery without granting a weaker alternate route to admin operations.

Implement authentication-strength and freshness checks where required. Verify the selected issuer's assurance claims and their behavior through token exchange; do not assume an exchanged token proves a recent MFA challenge. User-interactive reauthentication remains a browser OIDC flow, not a background grant.

Done when: Playwright with virtual WebAuthn authenticators exercises enrollment and login; generated test TOTP secrets exercise valid, invalid and replayed codes; recovery codes work once; credential removal and alternate-login paths cannot bypass the chosen policy. The same image and themed pages pass these checks.

Implement one complete protected service path

Use the existing OAuthTokenClient and operation-scope foundation. Add an authorization adapter and the organization-claim mapping at the infrastructure boundary. Implement one minimal real feature through a gateway and service; avoid creating placeholder business services.

Exchange caches must be bounded by token expiry and keyed by caller/session, audience, scopes and tenant context. Apply equally explicit boundaries to permission caching. Use HTTPS outside explicitly configured ambient-mTLS or isolated development transports; keep secrets out of tokens, event representations and logs.

Done when: real token exchange, allow/deny decisions and cross-tenant access tests pass over the actual protocols, with no mock authorization in acceptance tests.

Validate and connect KETE

Evaluate a pinned, verified KETE JAR in a separate opt-in image. The evaluation found mandatory administrative-representation retention, so the normal image remains KETE-free. Route only required user/admin events to a dedicated RabbitMQ exchange; verify organization create/update/disable/delete and membership event payloads. Configure confirmations/persistence where supported and demonstrate the delivery behavior rather than assuming defaults.

Build a Wolverine external-message adapter: validate allowed realm/resource types, deduplicate stable event IDs, refresh canonical state when an event is incomplete or stale. A future owning business service must define its own transactional projections and integration events; the shared adapter does not invent them. Account for duplicate and reordered events, deletion races and poison payloads. Use reconciliation to recover missed updates, and observe projection age and publication failures.

Done when: broker and process failure tests demonstrate recovery within the chosen freshness policy. If KETE cannot meet the requirement, keep live checks/reconciliation and treat events as an acceleration mechanism.

Use the same artifacts across local development and CI

Aspire, Testcontainers and KIND consume the same custom image and shared realm/policy definitions, with environment-specific issuer URLs, TLS and generated credentials. Development can use a faster theme iteration loop; acceptance always exercises the built artifact. Add explicit Nx dependency edges from theme/config/image changes to authentication tests.

Done when: the assembled browser journey and deployed Kubernetes journey pass, and an image/configuration change selects those suites in CI. Mobile test tooling remains undecided.

Evaluate optional GeoAware and MFA providers

Pin provider artifacts against the chosen Keycloak release and include only selected JARs. First prove GeoAware with deterministic local GeoIP data, trusted proxy forwarding and unfamiliar-device/location scenarios. Verify behavior for VPN/mobile-network changes, absent database entries and lookup failures. Start with notifications and bounded additional verification.

Evaluate guided enrollment and trusted-browser plugins separately. Test each selected provider with the theme, upgrade path and admin assurance policy. Configure a local mail sink for notification assertions. If KETE is used for related audit events, verify which events and fields are actually emitted; do not assume the providers expose every risk decision.

Done when: there is evidence that each added provider solves a concrete gap, retains required MFA on every alternate path and passes the exact image's integration/E2E matrix. Roll out optional flows only after these gates pass.

Current foundation versus planned work

Already present: Aspire Keycloak resource, basic teck-local realm and PKCE web client, OAuth token-exchange client, ITenantDirectory, operation scope and tenant isolation groundwork, Testcontainers.Keycloak dependency, discovery/health coverage.

Implementation status: the theme, native Organizations/AuthServices adapters, cache-backed canonical tenant store, MFA assurance, event invalidation and reconciliation are implemented. Component and browser evidence is recorded above; coverage/build, static-handler, assembled Aspire and full/reduced deployed KIND acceptance gates all pass. Optional adaptive-authentication providers remain deferred. KETE is an opt-in evaluation artifact because of its administrative-data retention behavior.

Keep the existing multi-tenancy, architecture, messaging and testing documents as the implemented contracts. Reconcile them as each phase lands; this proposal does not silently replace current runtime behavior.

Sources and validation notes

  • Keycloakify and documented shadcn alternative: build tooling and a package-based login theme option.
  • Keycloak administration: organization enablement, attributes and managed/unmanaged membership behavior.

  • Authorization Services: resource/scope policies and permission decisions.
  • MFA plugin collection, enrollment enforcement and trusted browsers: optional provider capabilities and maturity, not tested compatibility.
  • GeoAware, conditional authenticators and local MaxMind support: login signals and flow composition.
  • KETE overview, AMQP destination, transaction support and retry behavior: capability references, not evidence of tested Teck.Cloud integration.
