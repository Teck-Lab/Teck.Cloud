# Keycloak theme

Pinned keycloak-shadcn starter, built with Bun, Nx and Keycloakify for the shared Keycloak 26.8.2 image. Login, organization selection, MFA/passkey/recovery and legacy multi-page account pages are retained. This is a browser theme served by Keycloak, not a standalone authentication authority.

## Build and use

From the repository root:

- `bun nx run keycloak-theme:typecheck`
- `bun nx run keycloak-theme:build`
- `bun nx run keycloak-theme:test`
- `bun nx run keycloak-theme:container:build` (Docker or Podman)

The image target follows Aspire's `ASPIRE_CONTAINER_RUNTIME`: `docker` by default, or `podman`. Only those two executable names are accepted; the builder launches the selected engine directly without a shell. Run it against the same engine used by Aspire/Testcontainers so the local candidate image is available.

The image target builds the theme from source using the root frozen Bun lock and Maven inside the builder. It produces `localhost/teck/keycloak:26.8.2-theme-local` with one `teck-keycloak-theme.jar`, then runs Keycloak's optimized PostgreSQL build. Maven/Java/Node build tools are not included in the final image. Run with PostgreSQL and normal Keycloak configuration; set realm `loginTheme` and `accountTheme` to `teck`. Do not use this image tag as a published immutable release. Release CI must publish its resulting digest; the shared AppHost identity runtime descriptor then lets Testcontainers, Aspire and Kubernetes select the same image. Consumers must depend on the `keycloak-theme` Nx project.

For a host-only JAR build, `bun nx run keycloak-theme:build:theme` additionally needs Java and Maven on PATH. Keycloakify internally invokes local npm/npx tooling; Bun remains the dependency owner. No global or floating Keycloakify install is used.

The active light/dark palette comes from the shared design-token package in src/packages/design-tokens. Its generated CSS is imported after the pinned starter stylesheet, overriding the starter variables without editing upstream source. Change tokens.json and regenerate the package to update the login and native security pages together. Future web and React Native apps consume the same package; none exists yet in this repository.

## Ownership and upstream updates

`upstream.json` pins provenance; `LICENSE` retains upstream MIT attribution. Source under `src/vendor/keycloak-theme` and static assets under `vendor/keycloak-shadcn` are imported third-party code, excluded only from Biome's rewriting/linting. They remain in strict TypeScript checking and application builds. Authored entry point, branding, build configuration and tests remain linted. Keep security pages when updating the snapshot.

The small listed source adaptations guard indexed accesses under the repository's TypeScript6/noUncheckedIndexedAccess policy; `kc.gen.tsx` is regenerated by Keycloakify for theme name `teck`. The authored entry point uses only the server-supplied context, without upstream's fabricated realm fallback. Vite aliases the branding hook to `src/branding.ts`: no extra Java SPI, experimental admin UI, public realm-attribute endpoint or background theme-config fetch. Upstream's unused entry/config/story files are preserved for reviewability and are not application entry points. Static logos use the included starter assets until Teck branding assets are supplied.

No KETE, GeoAware or optional MFA provider is installed. The retained Keycloak UI pages do not enable providers or authentication policies on their own.

## Native security pages

The upstream custom OTP configuration, WebAuthn registration and recovery input
pages omit protocol fields or browser credential operations needed by Keycloak.
`login/KcPage.tsx` therefore delegates OTP, WebAuthn, passkey, recovery and
organization selection to Keycloakify's native `DefaultPage`, styled by the authored
`src/security-theme.ts`. The original upstream page source remains archived for
provenance; it is not selected at runtime. Do not restore those custom cases merely
to match the starter screenshot. Native hidden fields, user-verification operations,
recovery confirmation and server error handling are part of the authentication
contract, not optional presentation details.

The shared realm's built-in MFA policy and test boundaries are documented in
[identity MFA](../../../docs/identity-mfa.md).
